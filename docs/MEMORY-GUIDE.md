# 記憶體怎麼運作：事件流、索引與快照

## 三層，職責不同

一條 loop 的記憶分成三層。**只有第一層是真相**，其餘都是可以整個刪掉重建的衍生物。

| 層 | 是什麼 | 誰讀它 | 壞掉會怎樣 |
|---|---|---|---|
| **事件流**（`.loops/<slug>/events.jsonl`） | 只增不改的精確紀錄，每行一筆事件 | 機器 | **這才是問題**——它是稽核依據 |
| **索引**（`.loops/.index/`） | 由事件流重建的工作圖 ＋ 全文搜尋 | 機器 | 刪掉重建就好 |
| **快照**（`loop.md`、`PROGRESS.md`） | 給人看的當前狀態 ＋ 最近必要事件 | **你** | 下次自動重生 |

## 為什麼要這樣分

以前 `loop.md` 同時是狀態、摘要與**會無限長大的流水帳**。結果是：每個階段都要整包重讀一份越來越長的檔案，而人真正想知道的「現在卡在哪」反而被淹沒。

現在分開之後：

- **機器讀事件流**——精確、可 replay、可稽核。
- **人讀快照**——長度有界（最多十來筆最近事件，高訊號的優先），一眼看得到「還有什麼擋著」。
- **完整歷史永遠在事件流裡**，沒有被丟掉，只是不再塞進每次都要讀的那份檔案。

## 壞掉的時候會怎樣

事件流是 append-only，所以壞法有限，而且每種都有明確行為：

| 情形 | 行為 |
|---|---|
| 寫到一半當機（最後一行不完整） | **丟掉那半行、回報這件事**，前面的事件完好 |
| 中間某行壞了 | 嚴格判定停在**最早**那一行並指名行號；唯讀展示回「到那一行為止」的狀態，並顯眼標出停在哪 |
| 讀到未知版本 | 同上，並指名版本號——**不猜語意、不跳過續讀** |
| 同一筆事件重複 | 去重（狀態與只出現一次相同），但**回報偵測到重複** |

**明文禁止「跳過壞掉的事件繼續讀」**：停在第一個壞事件產出的是「這條 loop 在第 N 筆事件時的樣子」——本身是完全正確的歷史狀態；跳過續讀產出的是中間有洞的狀態，而閘會拿它做判斷。那正是整份設計要防的形狀。

## 事件流永遠不會被裁切

它是稽核依據，不是本地統計檔。**不 rotate、不留最後 N 行、不壓縮**。

「無界成長」這個問題要解的是**人與 AI 每回合重讀的那份檔案**，不是機器逐行讀的事件流。裁切它會把「中段損壞」從「幾乎不會發生」變成「必然發生」，而且尾端檢查完全偵測不到中間的洞。

## 索引：可以整個刪掉

工作圖與全文搜尋都存在一個可丟棄的索引裡。**刪掉整個索引再重建，必須得到逐欄位相同的結果**——這是設計要求，也有測試在守。

全文搜尋是**附加品**：它壞掉只會讓模糊搜尋降級成慢一點的掃描，**不影響精確查詢、不影響「還有什麼擋著收圈」的判定、也不影響稽核紀錄**。

## 不要把向量檢索當成權威狀態

這套系統**沒有**把狀態判定交給向量檢索或語意相似度。

理由：閘要拿狀態做判斷（「還有沒有未修的嚴重問題」「這個階段有沒有跑過驗證」），這類判斷**必須是確定的**。相似度檢索回傳的是「比較像的東西」，不是「事實」。向量若要用，只能當**衍生的輔助索引**——找得快一點，但不決定任何事。

## 快照裡有什麼

`loop.md` 與 `PROGRESS.md` 由事件流重生，包含：

- 欄位表（類型、階段、回環數、停止條件）。
- **仍擋著收圈的**：未修的嚴重問題、沒過的閘、未決的決策、未解決的未知事項。
- 未完成任務。
- 四象限未知事項摘要（如果這條 loop 有的話）。
- 最近事件（**有界**，高訊號優先——不會被一堆工具呼叫紀錄淹沒）。
- 事件流本身有問題時（例如上次寫到一半當機），**警告會顯示在最上面**。

**手改快照沒有意義**——下次重生就蓋掉了。要改狀態，就往事件流加一筆事件。

## 接續中斷的工作

```
/loops-workflow:dispatch <slug>
```

它會 replay 事件流重建狀態、回報停在哪個階段與哪個閘，再問你要不要續跑。這條路徑**不依賴對話記憶**——換一台機器、隔一個月都一樣。

## 怎麼驗證

1. 跑一條 loop 到一半，把 `.loops/.index/` **整個刪掉**，再讓它重建 → 工作圖應該一模一樣。
2. 打開 `loop.md`，手動改一行，讓它重生一次 → 你的改動應該消失（證明它真的是 generated）。
3. 用 `dispatch <slug>` 接續，確認它報得出「停在哪個階段、還有什麼擋著」。
4. 想看完整歷史，直接 `tail` 那份事件流——它是純文字、一行一筆，不需要任何工具就讀得懂。
