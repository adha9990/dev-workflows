# 一條 loop 會發生什麼、你要在哪裡把關

這份文件講**你的角色**：哪些地方它會停下來等你、哪些地方它自己往下、以及完工時你會拿到什麼。

## 一句話

```
/loops-workflow:dispatch <你想做的事>
```

它會判斷這是什麼類型的工作、開一條 loop、然後一路往下跑：釐清 → 開票 → 設目標 → 探索做法 → 拍板規劃 → 寫 code → 獨立審查 → 修到好 → 開 PR。

## 每件工作都要有一張票

**先有 issue 才動工**——包括「只是研究一下」。理由很實際：沒有票的工作追不回來，PR 也沒有可以關聯的東西。

你不需要自己開票：說出你想做什麼，它會把模糊的想法收斂成一張格式完整的 issue 再開始。**沒有獨立的「研究 issue」**——研究永遠服務某個功能，要嘛是某張功能票的探索階段，要嘛先研究完再開功能票。

## 它會依這件事的大小調整投入

同一套流程套在「改一段文案」和「改一條交易邊界」上，付的基礎成本幾乎一樣——完整施工圖、機制圖、對齊留言、三份完工文件、收尾裁測，每一件都跑一遍。所以 loop 一開始會先判**這件事該投多少**，分三檔：

| 檔位 | 什麼時候 | 差在哪 |
|---|---|---|
| **直行** | 小、原因明確、範圍收斂、用既有測試就驗得出來、不碰高風險的東西 | 施工圖出一頁、免機制圖、對齊留言出精簡版、完工交一份合併的交付說明、回環軟上限 2 圈 |
| **標準**（預設） | 判不出來就是它 | 現行完整流程，一個字都沒少 |
| **加強** | 碰到登入權限／密鑰／金流／資料庫結構變更／對外介面／並發／部署設定，或範圍大、做法還沒定 | 審查員全派＋深審變體，設計來回審到乾淨為止 |

三件你可以檢查的事：

- **省的是文件的厚度與來回的次數，不是把關**。開票、進 code 前的拍板、獨立審查、機械閘、真機驗證、「重大問題沒清乾淨不准送審」——**每一檔都照做**。
- **判不出來一律走標準檔**，不是走最省的那檔。「直行」要七條前提**全部**成立才算。
- **只會往上調，不會往下**。做到一半發現碰了高風險的東西、範圍變大、冒出說不清楚的問題、或審查抓到嚴重缺陷，它會**當下升一檔並回頭補做**，並告訴你為什麼。反過來想調低，要你點頭，而且只有「當初升檔的理由被查證是誤判」這一種情況。

送審前有一道機械檢查：如果這條 loop 宣稱走「直行」，實際卻改到了高風險的東西，開 PR 會被擋下來，要求升檔補做——省流程的前提是**判準真的成立**。

## 它會在哪裡停下來問你

**階段之間不會問**。做完一個階段就往下，不會每次都問「要不要繼續」——那只是把決策成本轉嫁給你。

會停的只有兩種：

**真的要你選的決策**
- 探索完，要選哪個做法。
- 規劃完，拍板方案（含要不要引入某個套件）。
- 驗證完，要收工還是回頭再修。
- 範圍取捨：這個要做嗎、那個先不做嗎。

**安全停點（一定停）**
- 分類不明確，不知道你要什麼。
- 危險或不可逆的操作。
- 審查出最高等級的問題。
- 規格講不清楚，猜了會做錯方向。
- **還有沒修完的嚴重問題，卻要收工**。

你隨時可以插話喊停或改方向，不用等它問。

## 把「沒人寫下來的東西」問出來

真正拖垮開發的常常不是已知的難題，而是**沒被問出來的東西**：你知道但沒寫下來的規則、以及雙方都沒想到的盲點。

風險夠高時它會走一段訪談，把這些整理成一份**四象限清單**：

| 象限 | 是什麼 |
|---|---|
| 已知的已知 | 你明說過、或查得到證據的事 |
| 已知的未知 | 已經知道要問、但還沒有答案 |
| 未知的已知 | 你沒寫下來、但**看到例子就認得出來**的隱性規則 |
| 未知的未知 | 探索程式碼、外部研究或審查時才冒出來的盲點 |

三條規矩：

- **一次只問一題**，帶推薦選項與理由。
- **查得到的不問你**——「這個專案用什麼測試框架」它自己去看，只有會改變範圍、行為、驗收或架構的**決策**才問你。
- **AI 自己的假設不會被寫成「已確認的事實」**——那要經過查證或你拍板。

**影響範圍、介面、資料、安全、架構或驗收的未決事項，沒解決前不會開始寫 code。** 這不是禮貌性提醒，是機械擋下的。

另外：**它不會宣稱「盲點已經清零」**——那不可知。它只記錄「做過哪幾種盤查」與「還有哪些殘餘風險」。

## 進度看哪裡

- **開場**會自動浮出還沒完工的 loop。
- **隨時想看**：直接開 `.loops/<slug>/PROGRESS.md`——每回合自動重生，包含階段進度、目前擋著的事項、四象限摘要與最近事件。

## 完工你會拿到什麼

一條完整的 loop 收工時產這幾份東西（**走「直行」檔位時合成一份 `delivery-note.md`**，內容一樣是這三段——縮的是份數，不是內容）：

| 檔案 | 是什麼 | 為什麼需要它 |
|---|---|---|
| `explain.md` | **實作導讀**：做了什麼、怎麼運作、設計方向回顧，加上幾題自測 | 防「理解債」——code 跑得比你讀得快，落差會一圈圈累積 |
| `checklist.md` | 合併前你要手動驗證的清單 ＋ 已知取捨 | 有些事只有人眼判得出來 |
| `cost.md` | 這條 loop 花了多少（token、子代理數、回環圈數、findings） | 讓成本看得見，而不只是「有意識」 |

**這幾份是給你讀的，不是交差用的。** 特別是實作導讀——它存在的唯一理由是讓你重新拿回對這段 code 的所有權。寫不出導讀就代表沒人讀得懂這次改動，那這條 loop 本來就不該走最省的檔位。

## 為什麼要有這些把關

兩個具名的失敗模式：

- **理解債**：loop 跑得快、產出你沒讀懂的 code。落差每一圈都在累積，直到某天你完全不敢動它。→ 對策是完工一律產實作導讀（`explain.md`，直行檔位併進 `delivery-note.md`）。
- **認知投降**：被動讓它跑、不再維持自己的判斷。→ 對策是決策點停下讓你把關，以及「沒實測就不准寫數字」的紀律。

這兩件事不是流程冗餘，是這套設計要防的具體風險。

## 驗證你自己走過一遍

1. 用一句話開一條 loop，看它有沒有先幫你把票開好。
2. 在「選做法」那個決策點，故意選非推薦的選項，看它有沒有照你的選擇走。
3. 中途關掉 session，隔天用 `dispatch <slug>` 接續，看它能不能重建狀態。
4. 完工後打開實作導讀，問自己：**如果現在要我改這段 code，我知道從哪裡下手嗎？** 答不出來就把問題丟回去。
5. 丟一件很小的工作進去（改個錯字、調一處樣式），看它有沒有判成「直行」——以及有沒有還是照樣停在進 code 前的拍板點問你。**該省的省了、該停的還是停**，這條規則才算生效。
