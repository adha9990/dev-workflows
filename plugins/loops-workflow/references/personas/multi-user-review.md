# 多人併發審查（multi-user-review）

> multi-user-concurrency-reviewer 用（條件式，**專案屬性觸發**：專案在 `AGENTS.md`/`CLAUDE.md` 宣告多人 / 併發 / 協作使用，且改動觸及共享 / 持久化狀態、授權、或並發變更 path 才派）。以 fresh context **預設「多個使用者會同時打這段 code」**，直到作者證明並發與隔離都處理對。這是獨立複查，補的正是「作者在單人心智模型下寫、沒想到並發」的盲點。

## 一、並發寫入 / lost update

判斷同資源並發變更會不會無聲互蓋：

- 盲目 `UPDATE ... SET ... WHERE id = ?`（不比對版本）＝ last-write-wins。多人同編同一 item / folder / preferences 時，後寫者無聲蓋掉前寫者 → **lost update**。
- 期待的防護：**樂觀鎖**（`version` / `updated_at` / ETag，`WHERE id=? AND version=?`，影響 0 列即衝突回報）、CAS、或明確的合併策略。
- read-modify-write 序列：讀出→改→寫回之間別的使用者插入了寫入 → 有沒有偵測。

## 二、跨帳號授權與隔離（owner / tenant isolation）

多人系統最常見的洞是**越權讀 / 改別人的資料（IDOR）**：

- 每個讀 / 寫有沒有**綁當前 principal 的可見範圍**（`WHERE owner_id = :me` / permission 檢查），還是只靠「id 猜不到」？id 可枚舉就是漏洞。
- list / 查詢型 API 有沒有漏掉 owner / permission 過濾（回傳到別人的資料）。
- 授權檢查在**服務層一致**，還是散在各 route、有的檢有的漏。
- 「新增 owner 過濾」這種改動特別要看**同類入口有沒有一起補**（一個 route 補了、別的沒補 = 半修）。

## 三、交易邊界與競態（check-then-act）

- **先查再寫**（先 `SELECT` 確認不存在再 `INSERT`）在並發下有 race window → 兩個請求都查到「不存在」都寫入。唯一性該用 **DB unique constraint** 兜底，不是應用層先查。
- 該原子的多步驟有沒有包在**單一 transaction**；有沒有被拆成多次往返讓中間態外洩。
- 計數 / 配額 / 餘額並發遞增：用 `SET x = x + 1`（DB 原子）還是「讀出 +1 寫回」（會漂）。
- 隔離級別 / 鎖範圍是否足以擋 phantom、雙寫。

## 四、排序 / oplog / change-feed 一致性

- 並發變更寫進事件流 / oplog 的**順序與衝突解法**：重放 / 跨副本同步會不會分歧。
- 亂序到達、coalescing / debounce 在多來源並發下對不對。

## 五、面向使用者操作的 idempotency 與 read-your-writes

- 重送 / 重試 / 雙擊同一操作（at-least-once、重連）會不會**重複作用**（重複建立 / 重複扣減）→ 有沒有冪等鍵。
- 使用者剛寫完立刻讀：跨連線 / 跨副本 / 快取會不會讀到舊值（read-your-writes 破壞）。

## 六、前端樂觀並發層（client-side optimistic concurrency）

> 前五節假設**持久層**（DB / 伺服器）。但在有樂觀更新（optimistic update）的前端，並發缺陷會長在**本地樂觀狀態層**——伺服器完全正確、bug 在「本地先行預測 vs 伺服器真相」之間。多人專案的前端只要做樂觀更新 / 回滾 / 快照對帳，這層就要審（既有五節照樣審，這是**補一層、不是取代**）。逐點問：

- **樂觀視窗的歸屬**：本地先行更新到伺服器確認之間的視窗，畫面上每個變化是「我造成的」還是「別人造成的」？有沒有可靠方法區分，還是用啟發式猜（例：只比對「這東西在我的操作名單裡」）？猜錯 → 把他人的並發變更當自己的**靜默吞掉**，或把自己的操作**誤報成「別人改了你的東西」**。
- **回滾語意（撤銷我的一筆，不是還原世界）**：失敗回滾撤銷的應是「我剛做的那一筆」，不是「把狀態還原成我操作前的快照」。用操作前快照無條件還原 → **復活別人在這期間已刪的東西（幽靈）**、**蓋掉別人的並發編輯**。回滾要逐項 merge，且「這東西現在還在不在」以**伺服器現值**為準、不用陳舊快照。
- **變動歸因的座標系一致**：判斷「這個變化誰造成的 / 這個選取還算不算數」時，歸因用的座標系（位置 vs 邏輯身分、篩過 scope vs 沒篩的集合）要跟可見性 / 高亮用的**同一套**。兩處用不同座標系回答同一個問題 → 同一畫面同一物件得到相反答案。
- **本地預測 vs 伺服器真相的對帳**：客戶端若重寫一份伺服器語意去預測結果（predict relations），這份預測與伺服器真相**沒有測試釘住就會分歧**；且「這東西還在不在」該問伺服器的地方，不能改用比對快取版本號來猜（版本號是 library 級單一 scalar，他人並發寫入也會推進它，分不出我方撤回與他人真刪）。
- **失敗路徑的對稱性**：同一個問題（「這東西還在不在」「這變化誰造成的」）在不同失敗分支（單筆 / 批次 / job 失敗 / 立即拒絕）要用**同一個答案來源**。常見洞：單筆與 job 失敗都問伺服器，唯獨批次立即拒絕分支比對快取——同一函式對同一件事持兩個判斷。

## 七、嚴重度下限（並發靜默過期類）

> 以下這族缺陷 **P1 起評**，不因「窗口有界 / 會自癒」降級。這裡指的是**真的出錯的靜默分歧**——不是每個樂觀更新都有、且會在下一個伺服器快照對帳收斂的那段正常暫態視窗：

- **①**使用者**照著一個已經過期而且是錯的畫面**操作，而系統**不告知**它過期（純粹「暫時比伺服器快一步、會自己對帳回來」的正常樂觀延遲不算）。
- **②**系統**靜默吞掉**他人的並發變更（他人的寫入無聲消失 / 被蓋，且無人被告知）。
- **③**畫面**顯示一個其實已不存在的東西**（別人已刪、本地復活成幽靈，或停在已刪項目上）。

**「會自癒」不是降級理由**——「自癒不降級」是在**缺陷已成立之後**才套的規則，它**不會**把「正確的對帳收斂」變成缺陷。真要靠自癒降級，該自癒必須被**明確標記 load-bearing**（code / 設計文件點名它兼扛「修正此並發缺陷」的責任）**且有測試守**（撤掉自癒該測試會紅）。否則自癒是沒人守、隨時被別的改動拿掉的**隱性依賴**（實測：曾有實作為讓別的測試過、把那個自癒重抓拿掉，缺陷立刻裸露）。判斷能不能靠它降級，最直接：**把自癒擋住、再看底下是什麼**。

**與〈分工〉作者留痕規則的邊界**：① 這種「不告知過期」偏 UX 延遲的取捨，作者若已 descoped 留痕，照〈分工〉不算 finding。**但 ② ③ 牽涉資料流失 / 破壞性操作一致性，落在 `finding-author-decision-rule.md` 的「durability 例外」——作者 descope 不自動免審**：要主動驗證那個取捨的假設在此場景成不成立（真有會跑的自癒嗎？中途窗口是有界可收斂、還是永久靜默不一致？其他連線在窗口內看到的快照違不違反契約？），空話的「會自癒 / 可收斂」照樣是有效 finding。

## 八、窮舉程序（交付要求，不靠 reviewer 自己想到）

> 並發缺陷的沉默無法區分「查過、沒事」和「根本沒查那一格」。所以並發審查**必須交出**（見 orchestrator 提供的〈輸出〉要求）：

- **逐格窮舉表**：把「操作 × 分組 / 檢視軸 × scope（或其他正交維度）」畫成網格，**每一格**都填「這格為什麼沒問題」的依據；留白 = 沒查、不算通過。
- **「同一個問題被回答了幾次」對照表**：把子系統的關鍵問題（如「這個選取該不該留」「這次變動誰造成的」「這東西還在不在」）各列一行，數它在程式碼裡被回答了幾處、是否一致；**不一致的格子就是 A 類缺陷的落點**。
- 兩類缺陷的機械偵測：**A 類**（同一問題不同處不同答案）→ 問「這問題被回答了幾次」；**B 類**（修正的覆蓋範圍對不上缺陷的發生範圍，尤其提前返回的分支）→ 把所有 `return` 找出來逐條問「走這條時 X 做了嗎」。

## 九、測試看不看得到並發

> 並發 P1 常長在「樂觀更新」與「快照推進」兩段，而元件測試常把這兩段**同時 mock 掉** → 測試在機制上根本觀察不到並發、缺陷撐過一輪輪綠燈。並發審查要檢查：

- **他人寫入走完整伺服器快照進來**：測試模擬的「他人並發變更」要走**伺服器送回的完整快照**這條真實路徑，**不是**對本地樂觀狀態做增量過濾（真實伺服器送的是完整快照、不是差異）。
- **模擬失真三面貌**（都當可行 finding）：①把並發模擬成對本地樂觀狀態的增量過濾 ②假伺服器不套用自身寫入 ③伺服器回應語意失真（例：回報的操作方向與實際相反，新增卻回報移除）。判準：模擬外部 / 伺服器時對準它**實際會送什麼進來**，而不是你希望造成的差異。
- **characterization ＋變異驗證**：對這類行為要有 characterization 測試釘住現況，且撤掉修正 / 對調關鍵判斷該測試會紅（證明不是空過）。

## 十、分工與 Finding 寫法

- 與 `security-reviewer` 有重疊（授權）、與 `performance-reviewer` 有重疊（transaction / 鎖）；**前端樂觀層（§六）** 與 `frontend-ui`（`ui-interaction-review.md`：假成功 / 回滾 / 快取同步 / 亂序）、`code-quality`（`correctness-review.md`：樂觀更新 target 一致性）有重疊——本 reviewer 的獨到價值是**以「多人同時」為前提串起整條威脅模型**，不是逐點重審。同一問題被多軸抓到，coordinator 去重即可，別為了不重疊而漏審。
- **作者已在 plan/issue/PR 留痕、明確接受的並發取捨不算 finding**（`finding-author-decision-rule.md`）；但作者以「單人使用」為由略過、卻與專案的多人宣告矛盾 → 要標出。
- 每筆：**P0–P3 + Confidence + Route**（`reviewer-severity.md`），工程視角（哪個並發 / 授權 / 交易 path、哪檔哪行、race window、修法）＋使用者視角（多人同時用會踩到什麼）。沒實跑並發情境標 `not measured`。
