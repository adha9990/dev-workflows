# docs 規範（什麼該寫、什麼別寫、何時更新規範檔）

> 目的：讓「後續維護者看得懂」，同時避免「隨便小功能就塞 docs/」。在 build 完成 / iterate 收尾時，把「該不該補 docs」當成完工定義的一部分。

## 何時寫 `docs/<topic>.md`

命中**任一**就寫：
- **新子系統**（logging / i18n / auth / 權限 / 快取…）。
- **跨切面關注點**（影響多模組、不屬單一檔案）。
- **未來維護者光看 code 看不懂的設計決策 / 約定**（為什麼這樣切、有什麼坑）。

## 何時不寫

- 單一小功能、看 code 就懂的。
- 一次性 / 即將被取代的。
- 只是 API 列表（那交給型別 / 簽章，不要 docs dump）。
- **決策敘事 / 迭代過程 / 設計取捨流水帳** —— `docs/` 只放**教學與說明**（怎麼用 / 怎麼運作）；「為什麼這樣決定、評估了哪些方案、改了幾版」屬於設計計畫（`stages/02-plan.md`）/ PR body / git history，**不進 `docs/`**。
  - **注意「決策」有兩種，這條只排除其一**：被排除的是**決策敘事**（一次性——回答「**當初**為什麼這樣做」：為什麼選這設計、否決了什麼、研究過程）；**操作型決策準則**（重複性——回答「**下次**遇到新案例怎麼判斷」：該不該做 X／用哪個變體／門檻多少）是 **How-to、屬 docs**，見〈操作型決策準則〉節。把準則連坐排除，會讓 doc 只教機制怎麼動、不教維護者怎麼對新案例下判斷。

## 必要性 gate（開新 `docs/<topic>.md` 前必過 —— 防「弱觸發正當化整份 doc」）

「何時寫」的觸發命中 ≠ 就該開一份**獨立** doc。命中後先過這關，否則很容易「抓一個狹窄理由、開一份過度的教學 doc」：

1. **這塊非顯而易見的知識，是不是只有一段？** 若真正值得寫的只是「一個不變式 / 一個坑」（例：某排序鍵的 tie-break 有 3 個實作點要同步），**它該併進最貼近的既有 topic doc**（排序的坑→`item-query.md`）或**放成 code 註解**，不是為它單開一份帶圖的教學 doc。**先找既有的家，找不到才開新檔。**
2. **是不是單一 command / endpoint / 小功能？** 這類**預設不開** standalone doc（對齊「何時不寫」第一條）——看 code + 型別 + contract test 就懂。只有「新子系統」或「跨多模組、無單一既有 doc 承載的跨切面關注點」才值得一份新檔。
3. **觸發強度**：只靠**一個**狹窄理由（「這個欄位有點跨切面」）撐起整份教學 doc = 過度文件化。跨切面要到「多個模組、多個維護者會反覆踩、沒有既有 doc 放得下」才算數。

> 一句話：**先問「能不能塞進既有 doc / code 註解」，再問「要不要開新檔」。** 把「除 issue 外我做了什麼（i18n / logging…）」寫進教學 doc 是典型誤用 —— 那是 PR body 的事（見 `project-conventions.md`），docs 只教「這系統怎麼運作」。

## docs 寫什麼

**教學取向：怎麼用、有什麼限制 / 坑、怎麼擴充、擴充時怎麼判斷。** docs = 教學手冊（how-to），**不是決策敘事的紀錄** —— 「**為什麼這樣設計 / 取捨理由 / 被否決的方案**」屬於設計計畫（`design-plan-schema.md` §6 決策 / §8 三角驗證）與 PR body，不重複塞進 docs（docs 只在「不寫使用者會踩坑」時點到設計約定，不展開決策 audit）。但**操作型決策準則不在排除之列**——「擴充這系統時每次都要套的判斷」是教學的一部分（見下節）。不重貼 code、不寫成 API 字典。

## 操作型決策準則 —— 擴充時的重複判斷要成文且自足

系統若在**每次擴充時都要做同一類判斷**（例：新操作要不要加確認、用哪一段門檻；新事件要不要進 audit log；新欄位走哪種驗證），這個判斷準則就是 **How-to**（「我怎麼完成 X」的判斷步驟），**必須寫進該 topic doc**——用**準則表或判斷流程**呈現，讓讀者**不翻機制敘事、不翻任何 issue/PR** 就能對新案例下判斷。

- **判別式（一次性 vs 重複性）**：能改寫成「**下次遇到新案例怎麼判斷**」的條件句＝準則，進 docs；只回答「**當初**為什麼這樣做」＝敘事，進 plan / PR。騎牆例：門檻值本身（「超過 1000 筆才需要確認」）屬準則；「為什麼定 1000」屬敘事——準則旁的 why **最多一句、不指向票號**（同〈docs 必須自足〉）。
- **觸發時窗（不回溯存量）**：這條只在「本次**新增或實質擴充**該系統的 topic doc、或本次改動本身就是一次該重複判斷的實例」時要求；不拿它回頭要求所有既有 doc 補寫。
- **沒有重複性判斷就不硬塞**：單純「怎麼加一個 X」的線性步驟是〈操作指南〉的事，不用為它生一節準則。

## docs 必須自足 —— 不引用 issue/PR、不含狀態 / roadmap 段

`docs/<topic>.md` 是**獨立教學文檔**：讀者不必翻任何 issue/PR/loop 就能看懂「怎麼用 + 怎麼運作 + 有什麼限制」。把它想成「這系統已穩定存在很久」的教學手冊 —— 任何「這是最近做的 / 分幾期交付 / 見那張票」的痕跡都是雜訊，一律拿掉。

- **絕不引用 issue / PR 號**（`#NNN`、「見 issue #X」「承 #Y 研究報告」「設計脈絡見 PR #Z」）。要講的知識**直接寫進 doc**；要指更細，指**會留在 repo 的自足文件**：其他 `docs/<topic>.md`、各層 `AGENTS.md`/`CLAUDE.md`、程式碼 `file:line` / 型別。issue/PR 是過程產物，不是教學來源。（同理不引用 `.loops/` 路徑。）
- **不含狀態 / roadmap / 交付進度段**：「現狀與後續」「Phase 1/2（已交付）」「後續 follow-up」「roadmap」「里程碑」這類段落一律不進 docs —— 那是 PR body / plan / git history 的事。
- **用「限制」表達，不用「進度」表達**：現在做不到什麼、有什麼坑，寫成 **Reference / 限制**（「interpolation 參數型別不在檢查範圍」「只有部分 UI 走 t()、其餘 fallback en」）；**不要**寫成「哪個 phase 交付了 / 哪些是後續」。限制是教學（讀者會踩），進度是過程（讀者不需要）。
- **不寫里程碑名**（Phase 1 / Phase 2 / MVP…）—— doc 描述「系統現在怎樣」，不編年史。

## 寫給不懂、剛進來的人

doc 的讀者設定是**還不懂這個系統、剛進來的維護者**——要能從上到下讀懂，**不必先會**：

- **術語第一次出現就地解釋**：不把專案內部詞彙（函式名 / 設定鍵 / 內部概念）當讀者已知；第一次出現就用半句講清它是什麼。
- **先建心智模型，再上架構細節**：開頭給精簡的 Concept + 比喻 / 「跟著走一遍」，不要一開頭就丟架構表、通篇縮寫。
- **判斷標準**：一個沒碰過這系統的人照著讀，讀到每一段都知道自己在看什麼——做不到就是寫給已懂的人，重寫。

## 格式範本：Diátaxis 四型（教學手冊的骨架）

業界公認的文檔結構框架是 **Diátaxis**（diataxis.fr），把文檔分成四型、各答一個不同問題、**鐵則是分開不混**：

| 型 | 一句話 | 答什麼 |
|---|---|---|
| **Tutorial** | 牽著讀者走一遍學習體驗 | 我怎麼學會這個？ |
| **How-to** | 達成某目標的實際步驟 | 我怎麼完成 X？ |
| **Reference** | 事實 / 規格 / 查找 | 規格是什麼？ |
| **Explanation** | 背景、脈絡、**為什麼** | 為什麼這樣設計？ |

**本工作流家規 ＝ Diátaxis 減 Explanation**：本規範已把「為什麼 / 取捨」的**決策敘事**排除到 plan / PR，那正是 Diátaxis 的 Explanation 型。所以 `docs/` 只放 **How-to + Reference + 輕量 Concept（+ 可選一段 Tutorial 走一遍）**，「為什麼」最多一句帶過（**但不連 issue/PR 號** —— 見下方〈docs 必須自足〉）。**注意減的是敘事、不是準則**：〈操作型決策準則〉是 How-to 型（下次怎麼判斷），不是 Explanation（當初為什麼）——別把它當「為什麼」砍掉。使用者嫌 docs「太像決策手冊」時，通常就是混進了過多 Explanation。

**單一內部 feature → 一份檔、Diátaxis 顯性分節**（不必為純度拆成四個檔，避免碎片化 / 跨檔重複 / 維護成本）。章節明標類型即可：

```
# <功能>
> 一句話這是什麼（自足、教學取向；不引用 issue/PR、不寫交付進度）

## 概念｜心智模型（精簡的 Concept + 一個比喻，建立理解用）
## 教學｜跟著一次真實操作走一遍（Tutorial，用 mermaid 流程圖把真實資料流帶穿分層）
## 要不要／怎麼選（決策準則）（How-to 型：擴充這系統時要重複套用的判斷——準則表／判斷流程；只有系統確實有重複性擴充判斷時才需要這節，見〈操作型決策準則〉）
## 操作指南（How-to：怎麼新增 X / 怎麼擴充，可照抄步驟）
## 怎麼自己驗證（How-to：打 API / 查 DB / DevTools / 重載，讓讀者親手確認系統真的動）
## 參考（Reference：程式碼地圖 + 約束與不變式 + 值域 / 規格）
```

「跟著走一遍」那段是性價比最高的教學手法：用一個真實情境串過 UI→service→persistence→讀回，讀者一次看懂分層怎麼接。**範例程式碼必須對齊真實的型別 / 定義形狀**（讀者會照抄；欄位漏寫或名稱錯＝教錯）。

**圖用 mermaid、不用 ASCII art**：資料流 / 決策分支 / 注入接線畫成 ` ```mermaid ` flowchart（GitHub 原生渲染、好讀好維護、可複製），不要手畫 ASCII 箭頭圖（難維護、對齊易跑掉、螢幕閱讀器讀不出）。教學段每個關鍵流程配一張流程圖，勝過一大段文字。

**一定要有「怎麼自己驗證」段**：教學不能只講「系統怎麼動」，要給讀者**親手確認的方法** —— 打哪個 API 看什麼欄位、查資料庫哪張表、DevTools 看哪個請求、改完重載看什麼。這是「教會用」與「只描述」的分界；一份只描述、無從驗證的 docs 教不會人。

## 維護 `docs/README.md` 索引

每新增一個 `docs/<topic>.md`，就在 `docs/README.md` 補一行（標題 + 一句話）。沒有索引就一行：`- [logging](logging.md) — 日誌系統怎麼用 / 怎麼設計`。讓人從索引就能找到所有主題文件。

## 何時更新 `AGENTS.md` / `CLAUDE.md`

**只在「慣例 / 規則本身改變」時**，不是每個 feature：
- 新增一條團隊規範 / 開發約定。
- 改了分層約定、目錄結構約定。
- 新的命名 / 錯誤處理 / 測試慣例。

純功能改動**不動**這兩個檔。

### 怎麼寫（編輯 AGENTS.md / CLAUDE.md 的守門）

- **最小有用文檔**：每段都要回答「agent 讀了這段會做對什麼」——答不出就別寫。
- **Avoid**：不寫「be careful」式廢話；不貼決策流水帳／迭代過程（那是 issue/PR 的事）；不重複 README 已有的內容。
- **一次一 scope**：一次只更新一個段落／一個主題，不趁機大改整檔。

## 判斷流程

```
build 完成 / iterate 收尾
  ├─ 新子系統 / 跨切面 / 設計不直觀？ → 寫 docs/<topic>.md（+ 更新 docs/README.md 索引）
  ├─ 改了慣例 / 規則？             → 更新 AGENTS.md / CLAUDE.md
  └─ 單一小功能 · 看 code 就懂？     → 不寫（避免 docs/ 膨脹）
```
